==================================================
IDENTITY
==================================================

Firebase Authentication UID must become the canonical user ID everywhere.

Do not use:
- email as the primary ID
- handle as the primary ID
- Supabase UUIDs
- locally generated user IDs

Every user should map to:

users/{firebaseUid}

If the old Supabase user ID is referenced anywhere in the friends code, replace that relationship with Firebase UID.

==================================================
USER PROFILE
==================================================

Firestore:

users/{uid}

Example fields:

uid
email
name
handle
dateOfBirth
education
bio

updatedAt

The handle should be searchable.

Do not create duplicate user profiles.

==================================================
HANDLE SEARCH
==================================================

Port handle search from Supabase to Firestore.

A user's handle must be associated with their Firebase UID.

If handles must be unique, implement a proper uniqueness mechanism.

Do NOT rely only on:

query users where handle == X

followed by:

"if no result, allow creation"

because two users could attempt to claim the same handle simultaneously.

Use a transaction/reservation mechanism or a dedicated handle document such as:

handles/{normalizedHandle}

{
    uid: "firebaseUid"
}

The exact implementation should fit the existing architecture.

Normalize handles consistently for searching and uniqueness.

For example:

@JohnDoe
@johndoe
@JOHNDOE

should not accidentally become three different accounts if the application's intended behavior is case-insensitive.

==================================================
FRIEND REQUESTS
==================================================

Port friend requests to Firestore.

A reasonable structure is:

friendRequests/{requestId}

{
    senderId,
    receiverId,
    status,
    createdAt,
    updatedAt
}

or another structure if your audit of the existing implementation shows a better design.

Statuses can include:

pending
accepted
rejected
cancelled

Do not duplicate contradictory friendship state across many documents.

When a request is accepted, create the friendship relationship atomically.

==================================================
FRIENDSHIPS
==================================================

Represent an accepted friendship using Firebase UIDs.

Example:

friendships/{friendshipId}

{
    userA,
    userB,
    createdAt
}

Use a deterministic friendship ID based on the two UIDs so the same two users cannot accidentally create duplicate friendships.

For example, conceptually:

friendshipId = sorted(uid1, uid2).join("_")

Do not use random IDs for friendships unless there is a strong reason.

==================================================
MUTUAL FRIENDSHIPS
==================================================

Preserve the existing mutual-friend behavior.

A friendship should only exist after both users have accepted the relationship according to the application's existing logic.

Do not expose pending requests as friendships.

Do not allow one user to manually create a friendship document for another user.

Firestore Security Rules must enforce the relationship permissions.

==================================================
FRIENDS LIST
==================================================

The friends screen should retrieve the authenticated user's friendships using Firebase UID.

Then resolve the corresponding user profiles from:

users/{uid}

Do not use email matching.

Do not use handles as relationship identifiers.

==================================================
SECURITY
==================================================

This is critical.

Do NOT use:

allow read, write: if true;

Friend requests must only be writable by authorized users.

Users must not be able to modify another user's friendship state arbitrarily.

Users must not be able to impersonate another UID.

A user must not be able to submit:

senderId = someoneElse

and create a request pretending to be another person.

Always validate the authenticated Firebase UID using:

request.auth.uid

where appropriate.

Similarly, realtime presence must not allow arbitrary users to modify someone else's presence.

    → data usage if currently supported
    → lastUpdated

presence/{uid}

    → lastSeen
